The first foundation: metadata is not media

A YouTube watch page is an address for a content experience. It is not itself a playable audio file. Before playback, something must discover the video's identity, inspect available formats, and produce a concrete media descriptor.

What yt-dlp actually contributes

yt-dlp is primarily an extractor and downloader. In our proposed use, it runs briefly as a child process, performs the undocumented YouTube-specific work, selects an audio-only rendition, prints structured information, and exits.

Extraction mode: proposed
yt-dlp inspects YouTube
  - resolves video metadata
  - discovers available formats
  - chooses audio-only format
  - emits direct URL + request context
  - exits

AVPlayer later fetches media bytes
Download/pipe mode: alternative
yt-dlp inspects YouTube
  - chooses a format
  - opens the media URL itself
  - downloads every media byte
  - writes file or stdout
  - stays alive through playback

Another component consumes its bytes
Key distinction: using yt-dlp to obtain the URL does not mean yt-dlp must carry the audio bytes. It enters the byte path only if we ask it to download or pipe the selected media.

For an ordinary remote URL, AVFoundation performs the HTTP reads and decoding internally. Maro does not manually push each packet into AVPlayer.

The second foundation: access needs more than a URL sometimes

A direct media URL is often signed and temporary. The upstream server may also expect request context: cookies, a User-Agent, a Referer, IP affinity, or other behavior. A URL that works in yt-dlp can fail in another client if that client cannot reproduce the required context.

In the simplest design, yt-dlp appears only in the control plane. AVPlayer talks directly to the media CDN in the byte plane. That separation is the reason the direct option is small.

The seeking lab: a player does not always read front to back

A byte stream is an ordered series of bytes, but a media player often needs random access. It may read container metadata near one end, request an initial audio region, buffer ahead, then jump elsewhere when the user seeks.

Why HTTP Range matters

# Player asks for a specific region, not necessarily the whole object
GET /audio.m4a HTTP/1.1
Range: bytes=8388608-9437183

HTTP/1.1 206 Partial Content
Content-Range: bytes 8388608-9437183/16777216
Content-Length: 1048576
Content-Type: audio/mp4

A direct CDN can answer these requests itself. A local proxy must preserve the same semantics. A one-way stdout pipe cannot jump backward or forward unless another component buffers the content and implements random-access reads.

The hard proxy problem is not forwarding one GET. It is correctly serving repeated, concurrent, cancelled, and nonsequential reads without buffering an entire track into memory.

Direct compatible stream URL

yt-dlp resolves once; AVFoundation fetches and decodes the audio-only resource.

Smallest
WinsNo long-lived extractor, no local HTTP server, native seeking and buffering.
RisksFails when required request context or media format cannot be represented by AVFoundation.
RecoveryRe-extract on expiry/auth failure; mark incompatible formats unavailable.

Local loopback media proxy

AVPlayer sees a local URL. Maro makes each upstream request with extractor-supplied context.

Most control
WinsCan attach required headers, control redirects, refresh descriptors, and mediate ranges.
RisksMust implement secure loopback binding, streaming backpressure, cancellation, ranges, and HLS resource rewriting if used.
RecoveryRefresh upstream descriptor, recreate player item when byte identity cannot be guaranteed.

Extractor/transcoder stdout pipe

yt-dlp or FFmpeg stays alive and writes sequential bytes to another consumer.

Highest mismatch
WinsThe downloader reproduces its own request behavior; FFmpeg can remux or transcode.
RisksAVPlayer is URL/asset-oriented, stdout is nonseekable, and process/codec/CPU complexity expands.
RecoveryRequires buffering/spooling or a custom asset loader, effectively rebuilding the proxy problem.

The solution proposition is a staged boundary, not blind optimism

Proposed first release

Resolve one compatible audio-only URL, then let AVFoundation own the bytes

video selection
  yt-dlp.resolveAudio(videoId)
    require audio-only rendition
    require AVFoundation-compatible container + codec
    capture documented cookie / User-Agent context when present
  AVURLAsset(url, options)
  AVPlayerItem(asset)
  AVPlayer.replaceCurrentItem(item)
  play

on access expiry
  resolve a fresh descriptor
  recreate the player item
  seek near last known time

on unsupported header/protocol/codec
  return video_unavailable
  leave current playback unchanged

This choice preserves the PRD's requirement that no combined video/audio fallback is used. It also keeps the first release small. The limitation is explicit: a video is unavailable if its audio-only source cannot be played through the documented AVFoundation URL path.
