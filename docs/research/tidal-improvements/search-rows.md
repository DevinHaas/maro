No app/config edits, installation, live playback, or UI verification were performed. Existing unrelated working-tree changes were left intact. File pointers below are repository-relative unless absolute.

## Recommendation

Give search rows an explicitly bounded, flexible title column and roomier vertical rhythm; extract and adapt the existing native `ScrollingTitle`/`TitleViewport` from `PlayerWindow.swift:430–474` for search-row reuse. The user’s “animation we have in SketchyBar” may mean this compact player title, which already clips and animates full native text. Keep artwork and action hit regions fixed and separate. Decide the narrow-width arrangement before simply increasing every horizontal gap: at minimum window width there is already a real width-budget problem.

Implement only after review/spec. Search and Favorites share `SearchVideoRow`, so either accept the improvement in both or make the policy explicit. The dropdown preview and playlist rows are separate implementations and should not silently enter scope.

## Confirmed findings

- `Sources/MaroApp/SearchResultsView.swift:61`: full-result row is native SwiftUI. Its outer HStack has 12pt gaps; a separate 38pt play button precedes a nested button containing 52pt artwork, a 12pt gap, title/creator, and a zero-minimum spacer (`:74–95`). The nominal row height is 64pt (52pt artwork + 6pt top/bottom padding); results have only 4pt between rows (`:25`).
- Title and creator are one-line `Text`s (`:81–82`). There is no marquee, explicit title viewport, or title-column clipping. The nested label has no explicit flexible-width assignment; SwiftUI negotiates its width alongside fixed-duration/actions. This establishes the current structure, **not proof that SwiftUI actually overlaps pixels**.
- Row trailing reservations are a 60pt duration, 38pt favorite control, and 30pt menu label (`:87–94`). Global `AppIconButton` hit region is 38×38 (`Sources/MaroApp/AppDesign.swift:78–91`); changing that shared component would affect unrelated screens.
- `Sources/MaroApp/AppShellView.swift:14` reserves 280pt for the open sidebar below width 1200, 320pt above; shell horizontal padding is 16pt total and interpanel gap 8pt (`:12–26`). Search content adds 56pt horizontal padding (`SearchResultsView.swift:31`). Minimum window width is 760 (`SearchWindow.swift:20`), with an even smaller screen-fit exception (`:36`).
- **Derived width budget, not measured rendered geometry:** at 760pt with sidebar open, row width is approximately 400pt. Subtract row padding 16, fixed controls 166, four outer gaps 48, artwork 52, and its gap 12: approximately **106pt remains for metadata**. At 1024pt it is approximately 370pt. Increasing horizontal gaps alone worsens this. Native layout measurement is still needed to identify any actual compressed or overlapping child.
- Header spacing is independent hardcoding: “TITLE” starts at the left edge and “DURATION” uses `.padding(.trailing, 106)` (`SearchResultsView.swift:21–23`), so a row redesign should align the header using the same column metrics.
- Favorites instantiates the same row (`SearchResultsView.swift:52–54`). Dropdown preview has its own 48pt artwork and title at `GlobalSearchView.swift:46–65`; playlist rows have their own title at `PlaylistDetailView.swift:230–247`.
- Search remains mounted in a ZStack while hidden with opacity zero (`AppShellView.swift:17–20`). A marquee must receive route visibility explicitly; relying solely on `onDisappear` would let hidden search animations continue.

## Existing native component to reuse; distinguish it from the bar label

- Repo renderer passes the complete sanitized title, without length truncation (`integrations/sketchybar/plugins/maro.py:22–24,63–71`). Both anchors use `scroll_texts=on`, `label.max_chars=32`, `label.scroll_duration=100` (`:114–117`).
- Installed configuration points to `/Users/devinhasler/Applications/Maro Local/sketchybar/maro.sh` (`/Users/devinhasler/.config/sketchybar/sketchybarrc:113`). Its installed `maro.py:116` has those same three properties. Read-only binary version reports `sketchybar-v2.23.0`. No runtime item query or visual loop observation was made.
- Old progress notes mentioning a 28-character viewport/180-frame duration describe retired popup behavior (`docs/PROGRESS.md:1549`). They are not the current configuration.
- The bar-label renderer uses CoreText and its own animation machinery; its C renderer is separate from the reusable native compact-card component described below. The pinned [upstream text implementation](https://github.com/FelixKratz/SketchyBar/blob/6284ee816601486ace33ca48a0271832eec6de35/src/text.c#L274-L356) clips a full text line, moves it linearly left until fully out, jumps it to the right edge, then moves left to the start. It is a wraparound loop, not a back-and-forth bounce. First-leg duration scales with full-width/viewport-width; the return-to-start leg uses `scroll_duration`. The [v2.23.0 animation implementation](https://github.com/FelixKratz/SketchyBar/blob/v2.23.0/src/animation.c#L22-L25) converts duration units using 60 per second. Thus `100` is a base leg of about 1.67s, **not the duration of the entire title loop**. The pinned text-source revision was available; fetching v2.23.0 text.c failed, so exact installed text sequencing remains to be visually confirmed.
- **Correction after cross-report check:** `PlayerWindow.swift:206` uses `ScrollingTitle(title:)` at 18pt height. Its private `NSViewRepresentable` (`:431–435`) wraps the private AppKit `TitleViewport` (`:437–474`). The viewport masks to bounds (`:443`), holds the complete title and tooltip/accessibility label (`:450–455`), and measures the native `NSTextField` with `sizeToFit()` (`:462`). My earlier claim that no native marquee exists was incorrect.
- Native motion differs from the bar label: `CAKeyframeAnimation` translation values are `[0, 0, -overflow, -overflow, 0]`, key times `[0, 0.1, 0.8, 0.9, 1]`, duration `max(6, overflow / 25 + 3)` seconds, repeated indefinitely (`:467–472`). It pauses at the beginning, pans to expose the tail, pauses, and returns to the beginning; it does **not** wrap the text off one edge and reenter from the other. Preserve this existing motion by default unless review confirms the separate bar-label wraparound is intended.
- Extraction is feasible without a package or SketchyBar process dependency. Parameterize the current hardcoded 13pt semibold font/gray text (`:444–445`) so search retains its 14pt medium font and current-row Tidal color. Keep source metadata intact (4096 UTF-8 byte model limit, `Sources/MaroCore/PlayerState.swift:35`) and use native rendered width, not the bar's 32-character viewport.
- Current safeguards are useful but incomplete for lists: title/width/Reduce Motion participate in a layout signature (`:459`), and each layout resets/removes the old animation before deciding whether overflow warrants animation (`:462–466`). There is no active/visible input, appearance/disappearance cancellation, or observation that immediately invalidates layout when the OS Reduce Motion setting changes. Font changes also are not part of the signature. Add those contracts during reuse; do not claim current lifecycle/Reduce Motion observation is already complete. Reduced Motion currently leaves a static **hard-clipped full label** plus tooltip; ellipsis would be an additional behavior choice.

## Proposed scope and design decisions

1. `SearchResultsView.swift`: establish named row/header metrics; explicitly allocate a flexible metadata column, keep artwork/action sizes fixed, and clip only title drawing. Prototype 10pt vertical padding (72pt nominal row) and 6–8pt interrow spacing; treat these as review candidates, not approved specification. Retain current 12pt inner artwork/title separation initially and inspect the reported crowding with real native bounds.
2. Extract `ScrollingTitle` and `TitleViewport` into `Sources/MaroApp/ScrollingTitle.swift` (proposed) and keep `PlayerCard` using that same component. Add configurable font/color plus enabled/visible policy; retain measured overflow and existing keyframe motion. Reset on identity, text, font or width changes, and observe Reduce Motion changes. It must not affect sibling geometry or consume pointer events when nested in the search play button. Do not create a parallel marquee or make the whole title fixed-size without a constrained outer viewport. Coordinate extraction and title color parameters with the compact-card styling ticket.
3. Scope narrow-width behavior locally: prefer reduced content margins and a compact trailing arrangement, potentially moving duration beside creator at an explicit breakpoint. Preserve separate play/favorite/menu hit targets. Sidebar auto-collapse is a wider shell behavior decision and should not be smuggled into a row fix.
4. Use search-route visibility plus window/scene state, and stop work for offscreen rows. A `LazyVStack` alone does not establish exact viewport visibility. If all visible rows animate, use one lightweight presentation time source or verify per-row animation costs with the maximum revealed results.
5. Keep model/search/network/playback code unchanged except any minimal fixture injection needed to verify interactions.

Decisions for review: (a) whether “same animation” means the existing compact-card pan/return (recommended default) or the distinct bar-label wraparound, (b) all visible overflowing titles loop automatically versus hover/keyboard-focus activation, (c) Favorites included through the shared row, (d) compact duration placement or another approved narrow-width arrangement, (e) whether preview/playlist titles are explicitly deferred. None needs to block writing the specification; record chosen defaults there.

## Accessibility and lifecycle acceptance

- Honor SwiftUI [accessibilityReduceMotion](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducemotion): stop/reset movement and retain the existing static clipped-title fallback (or explicitly approve ellipsis). Provide full-title help and retain full accessibility labels for all modes.
- Existing row play label already carries the complete title/creator (`SearchResultsView.swift:86`). The marquee should not expose duplicated or changing accessibility elements if drawing multiple copies. Never announce every animation frame.
- If activation is hover-based, offer equivalent keyboard-focus behavior; a hover-only feature cannot be the only way to obtain full title text. Preserve all current enabled/disabled semantics and distinct actions.
- Reset/cancel on new search results, title changes, resize, leaving search, hiding/minimizing the window, and Reduce Motion changes. Re-enter with a readable starting title; no stacked timers or stale offsets.
